# 0026 - Releases are published by a tag workflow from a read-only build

- Status: accepted
- Date: 2026-10-31 (M6 change `publish-github-releases`)
- Amends: [0009](0009-release-versioning.md), the "Local release tasks, no CI" bullet and the tag shapes: a `v*` tag push now starts a publishing workflow, and `release:tag` also accepts a squash-merged release commit
- Amends: [0024](0024-hosted-ci-runs-every-offline-gate.md), the location of the gate steps only: they live in the reusable `.github/workflows/gates.yml`, which stays the single setter of `BLACKGRID_NO_GAMES_RUNNING`
- Source: [design](../../openspec/changes/publish-github-releases/design.md) D1-D7

## Context and problem

ADR-0025 produces a zip, a setup and `SHA256SUMS.txt`, but nothing publishes them: the release tags `v0.1.0`, `v0.4.0` and `v0.5.0` have no GitHub Release, and the files exist only on whichever machine ran `package:release`. Publishing needs a write token. The code that builds the bundle (Flutter, pub packages, CMake, the vision fetch, the qualification tests) is code from the tagged tree and its dependencies, so that token must never be in reach of it. A wrong or partial release is public to every collaborator, and a Windows runner for a private repository is billed. ADR-0009 also assumed a merge commit for release PRs, but the project merges with `squash`.

## Decision

- **One reusable gates workflow (D1).** The CI job's steps move to `.github/workflows/gates.yml` (`on: workflow_call`) with one optional string input, `release_tag` (default empty). `ci.yml` keeps its triggers and concurrency and calls it with no input; `release.yml` calls it with the tag. With `release_tag` set, the job checks out `refs/tags/<tag>`, adds the tag-tooling guard and the `verify-tag` step right after the mise install, and uploads the package after the Package step. The gate steps are identical in both modes and have no `if:`. The no-games confirmation stays on the one qualification step, now in `gates.yml`.
- **Three jobs, write permission only where no repository code runs (D2).** `release.yml` has top-level `permissions: contents: read` and:
  1. `preflight` (`ubuntu-latest`, no checkout, `contents: write`) resolves the tag (`github.ref_name` on push, the `tag` input on a manual run) and passes it to scripts only through `env:`. A manual run is refused unless `github.ref` is `refs/heads/main`, because `workflow_dispatch` runs the workflow files of the ref the user picks. The name must match `^v[0-9]` and the tag must exist on origin with `object.type` `tag` (the authoritative annotated-tag check); its `object.sha` becomes the output `tag_object`. It then lists releases (`gh api --paginate repos/$GITHUB_REPOSITORY/releases`, filtered on `tag_name`) and fails naming each match. It needs the write token because the Releases API lists drafts only to callers with push access.
  2. `gates` (`uses: ./.github/workflows/gates.yml`, `needs: preflight`, `contents: read`).
  3. `publish` (`ubuntu-latest`, `needs: [preflight, gates]`, `contents: write`) downloads the artifact, verifies it, repeats the release listing and creates the release. It has no checkout and no `mise`, and runs only `gh`, `sha256sum` and `jq`.

  An offline test asserts that a job with `contents: write` has no `actions/checkout`, no `mise` and no `uses:` of a local workflow.
- **Tag validation is a tested Dart subcommand, guarded for old trees (D3).** `release.dart verify-tag <tag> --out <dir>` (mise task `release:verify-tag`) runs inside the tag's checkout before Analyze. It refuses unless the name is `v` + `SemVer.parseRelease`, the tagged commit is on `git rev-list --first-parent origin/main`, its `pubspec.yaml` version equals the tag's version and its `CHANGELOG.md` has a non-empty `## <tag>` section. It writes `build/release-meta/notes.md` (the section body) and `release.json` (`{"tag","version","prerelease","latest"}`); `latest` is true only for a final version with the highest precedence among the final `v*` tags in the checkout. `build/release-meta/` sits outside `build/release/`, which `package` clears. A `pwsh` step fails with "<tag> predates release publishing" unless the tagged `mise.toml` defines both `release:verify-tag` and `package:release`; it runs from `gates.yml` at the workflow's ref, so it works for trees that lack the subcommand.
- **The package crosses jobs as one short-lived artifact, re-verified on arrival (D4).** After Package, `gates.yml` (release mode only) uploads `build/release/*` and `build/release-meta/*` as `release-<tag>` with `retention-days: 1`, `if-no-files-found: error` and `compression-level: 0`. `publish` downloads it into an empty directory, which must hold exactly the three package files plus `notes.md` and `release.json`; `sha256sum -c SHA256SUMS.txt` must pass with the sums file listing exactly the zip and the setup; and `SHA256SUMS.txt` must match `sums_sha256`, a job output `gates.yml` computes on the runner right after Package and exposes through `outputs:`. Without that output a consistent replacement of the whole artifact would pass. Both artifact actions are pinned by SHA.
- **Draft, upload, then publish (D5).** `publish` runs, in order: the release listing (refuse on any match); a re-read of `git/ref/tags/<tag>` that refuses if the tag is missing or its `object.sha` differs from `tag_object` (a POST for a missing tag creates one from the default branch); `POST /releases` with `draft: true`, `name` the tag, `body` from `notes.md` and `prerelease` from `release.json`, keeping `id` and `upload_url`; one upload call per file; `GET /releases/<id>`, which must list exactly the three asset names in state `uploaded`; and `PATCH /releases/<id>` with `draft: false` and `make_latest` true only when `release.json` says `latest` (so never for a prerelease). Every call after the create addresses the release by `id`, never by tag name. `concurrency: group: release-<tag>, cancel-in-progress: false` serializes a push run and a manual run for the same tag; the second fails in preflight.
- **`release:tag` accepts a squash-merged release (D6).** A single-parent `HEAD` whose subject matches `^chore\(release\): v(<semver>) \(#(\d+)\)$` takes the squash path. With the already-confirmed `PushIdentity` token, `pulls/<N>` must report `merged: true`, `merge_commit_sha == HEAD`, `head.ref == release/v<version>` and `commits == 1`; `pulls/<N>/commits` gives that one commit, whose subject must be `chore(release): v<version>`, whose parent must equal `HEAD^` and whose tree (`git/commits/<sha>` then `tree.sha`) must equal `git rev-parse HEAD^{tree}`. `<owner>/<repo>` comes from origin's HTTPS github.com fetch URL. The merge path is unchanged, and every later check (pubspec, tag absent, annotated tag, fenced push) is shared.
- **Tagging stays local, building moves to CI (D7).** The flow is `release:prepare`, PR, merge, `release:tag`, then CI publishes. `release:tag` prints the URL of the `release.yml` Actions page after pushing and no longer suggests `build:release`; `build:release` and `package:release` stay for checking a build before tagging. A manual run starts from `main` and takes a tag that has no release; it refuses older trees such as `v0.4.0` and `v0.5.0`. A failed publish can leave a draft, and the user deletes it on the Releases page before a manual run.

## Rejected alternatives

- **Copying the gate steps into `release.yml`:** the two lists would drift, and the no-games flag would gain a second setter, which the `continuous-integration` spec forbids.
- **A release job that downloads CI's artifact for the tagged commit:** a tag can point at a commit whose CI run is gone, expired or cancelled, and the published bundle would not come from the run that published it.
- **A read-only preflight that sees published releases only:** a leftover draft would be found only after the full Windows gate run, up to 120 billed minutes.
- **One Windows job with `contents: write` that builds and publishes:** the write token would be in the runner's context for every build step, even with `persist-credentials: false`.
- **Shell checks inline in YAML for tag validation:** they cannot be unit-tested offline, and the SemVer rules would be duplicated outside `semver.dart`.
- **Rebuilding in the publish job:** it needs Windows and write access in the same job.
- **`gh release create`, then `gh release view` or `edit` on the tag name:** a tag name is ambiguous among drafts.
- **Creating a published release in one call and relying on gh's ordering:** whether gh publishes before every upload succeeds is not documented, and a public release missing its setup is exactly what the spec forbids.
- **Deleting a leftover draft automatically on rerun:** the workflow cannot prove it created the draft, and deleting a release is not reversible.
- **Making the agent merge release PRs with a merge commit:** `merge_method` is project-wide, a human merge from the GitHub UI uses the repository setting, and the failure shows only after the merge, when the tag is due.
- **Comparing a regenerated changelog with the committed one on the squash path:** the section date comes from the commit time, so a release merged the day after `prepare` would be refused.
- **Moving tagging into CI (a `workflow_dispatch` that tags):** a tag pushed with `GITHUB_TOKEN` does not trigger other workflows, and it would widen CI's permissions to write refs.

## Consequences

- Every `v*` tag push builds, qualifies, packages and publishes from the tagged tree, and the published files are the ones that passed qualification in the same run.
- Windows minutes double for a release commit: CI on `main`, then the tag run. Accepted for that guarantee (owner decision, 2026-10-31).
- CI's check is now named `ci / <job name>`. No branch protection or ruleset references it today.
- Accepted gaps: two final versions released within one run's duration could both be marked Latest (ADR-0009's one minor per milestone makes it negligible), and a draft created by hand between publish's listing and its POST is not guarded.
- The `prepare` changelog heading for a `-beta.N` version is assumed to be `## v<version>`; a fixture test in this change proves or corrects it.
- **Reversal cost:** low for all seven decisions. They change workflow files, their tests and tagging logic only, and no stored format changes. Published releases and tags are permanent (ADR-0009), so a bad release is fixed by a new version.
