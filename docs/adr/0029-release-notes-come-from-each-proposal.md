# 0029 - Release notes come from each change's proposal

- Status: accepted
- Date: 2026-11-01 (change `adopt-proposal-release-notes`)
- Supersedes: 0009 ([ADR-0009](0009-release-versioning.md)), its "Changelog: one entry per merged PR" decision and the git-cliff parts of its rejected alternatives and consequences only. SemVer versions, release commits, build numbers, the local release tasks and the version define stay in force, as does the rest of ADR-0009.
- Source: change `adopt-proposal-release-notes` (design D1-D4, D7, D8)

## Context and problem

Blackgrid's release notes were git-cliff output: one line per merged PR, built from its conventional title (`*(add-windows-ci)* run every offline gate on hosted Windows CI (#63)`). They name the work, not what a player or developer gets. The user's other project, sh1ny/specwright, opens each release with a plain-language summary and lists `Added:`, `Changed:` and `Fixed:` items written in each change's proposal (its ADR 0015). The user asked for that format on every Blackgrid release. A PR title cannot carry a summary or that grouping, and it is fixed when the PR merges.

## Decision

- **Each proposal carries a `## Release Notes` section in specwright's format (D1).** It runs to the next `## ` heading or the end of `proposal.md`: a summary of at most 600 characters, then one or more of `### Added`, `### Changed`, `### Fixed` and `### Removed`, each at most once and holding only list items of at most 500 characters, with at least one item in the section (an empty heading beside one with items is allowed, as in `release.sh`). HTML comments and blank lines are ignored, and an indented line continues the item above it. Anything else makes the section invalid. The section is kept although `release.enabled` stays false: a `rules: proposal:` entry in `openspec/config.yaml` overrides the schema's "delete the section" instruction, `mise run release-notes -- --check <proposal.md>` checks one proposal, and a fast offline test fails when an in-flight proposal's section is missing or invalid. The Dart parser (`tool/release/src/release_notes.dart`) follows specwright's `release.sh notes --proposal` rules, so both accept the same sections.
- **`CHANGELOG.md` is the durable store; each release inserts one section (D2).** `release:prepare` inserts the new `## v<version> - <date>` section above the newest existing section and leaves every other section byte for byte. A final version removes the sections of its own prereleases (`v0.7.0-beta.*` for `0.7.0`). Nothing regenerates the file. The earlier sections were rewritten by hand once, in this change.
- **The release summary is an input to `prepare` (D3).** `release:prepare -- <version> --summary <text>` or `--summary-file <path>` (outside the checkout, since `prepare` refuses untracked files). The summary is collapsed to one line (every whitespace run, newlines included, becomes one space; the ends are trimmed), so a `## ` line in the file cannot cut the section short in `verify-tag`. `prepare` refuses before any gate when the collapsed summary is missing, blank or over 600 characters. It builds and validates the whole section in memory after its preconditions and before the gates, so "nothing to release" is refused before any gate and before the branch exists; only the pubspec edit and the `CHANGELOG.md` insert come after `checkout -b`. `mise run release-notes` prints the draft first (grouped items, warnings, and the first-parent commits no change covers), so the summary is written from what it shows.
- **The range is the archived proposals added on main's first-parent line since the last final tag (D4).** `git log --first-parent --diff-merges=first-parent --diff-filter=A` over `openspec/changes/archive/*/proposal.md`, from the latest final tag reachable from `HEAD` (all of history when there is none), oldest first. Prereleases do not bound it, so a final release lists the whole milestone. Each proposal is read at `HEAD`. The PR number comes offline from the commit that added the proposal: its trailing `(#N)` (squash) or `Merge pull request #N` (merge). An item that names no `#<n>` outside a code span gets ` (#<PR>)` appended. Items are grouped across changes under `Added:`, `Changed:`, `Fixed:` and `Removed:`, in range order.
- **A change without a valid section is listed, not refused (D7).** It appears under `Changes:` after the grouped items as `- <name> (#<PR>): <first sentence of its ## Why>`, and preview and `prepare` print a warning naming it and its first error. With no valid section in the range, the section is the summary and `Changes:` only. A release whose range holds no archived proposal at all is refused: there is nothing to release.
- **Bounds.** At most 1 000 changes in a range (refused above), proposals over 64 KB fall back to their name with a warning (size read with `git cat-file -s` first), 150 listed items then `…and <n> more items`, 100 `Changes:` lines then names only and `…and <n> more`.
- **History and the two published releases are rewritten once (D8).** The `v0.6.0`, `v0.5.0`, `v0.4.0` and `v0.1.0` sections of `CHANGELOG.md` are rewritten by hand in the new format from their archived proposals and PRs. The new `v0.6.0-beta.1` body, covering only what had landed by that tag, is kept as `openspec/changes/archive/<date>-adopt-proposal-release-notes/release-bodies/v0.6.0-beta.1.md`, because the `v0.6.0` release already removed that section from `CHANGELOG.md`. After this change merges, and only after the user approves both texts, the `v0.6.0-beta.1` and `v0.6.0` GitHub release bodies are replaced with `gh release edit --notes-file`. Tags are not touched.
- **One-time exception to `release-publishing`.** For those two published releases only, the GitHub release body no longer equals the tagged commit's `CHANGELOG.md` section, which the requirement "Release notes are the version's changelog section" asks of a publish. The requirement still governs every publish; this is a single owner-approved edit after publishing. The authoritative copy of the `v0.6.0` body is its section in `CHANGELOG.md` on main; for `v0.6.0-beta.1` it is the archived `release-bodies/v0.6.0-beta.1.md`.

## Rejected alternatives

- **Keep git-cliff and write better PR titles (D1).** A title holds neither a summary nor Added/Changed/Fixed grouping, and it is fixed at merge.
- **Turn on `release.enabled` and use specwright's `release.sh publish` (D1).** It creates the GitHub release itself, which the tag workflow's preflight refuses (a release already exists), and it ships no installer assets.
- **Regenerate the whole `CHANGELOG.md` from archived proposals on every release (D2).** The 33 proposals archived before this change have no section, so v0.1.0-v0.6.0 would collapse to bare Why lines and lose the hand-written history.
- **A placeholder summary replaced in the release PR, with `verify-tag` refusing the placeholder (D3).** The edit would be a second commit on the release PR, which `release:tag` refuses; amending the release commit by hand is easy to get wrong.
- **The last change's summary as the release summary, specwright's fallback (D3).** It describes one change, not the release.
- **Asking GitHub which PRs merged, as specwright's `release.sh` does (D4).** It needs the network and a login inside `prepare`; the commit subject already records the number offline.
- **Ranges between all tags (D4).** A final release must list the whole milestone (ADR-0009).
- **Shelling out to specwright's `release.sh` (D5).** It lives in `.claude/skills/`, which a Specwright update overwrites, needs bash and Python, and its range is GitHub-backed.
- **Refusing a release when an archived section is invalid (D7).** A typo in one archive would block the release until a fix PR lands, and an archive is not supposed to be edited.
- **Backfilling `## Release Notes` into archived proposals (D8).** It edits archives and still needs hand-written summaries.

## Consequences

- **Every proposal needs a valid `## Release Notes` section**, kept current during apply. CI fails on an in-flight proposal without one.
- **A release needs a summary.** Run `mise run release-notes` first, write the summary from its output into a file outside the checkout, then `mise run release:prepare -- <version> --summary-file <file>`.
- **PR titles no longer shape the release notes.** They still follow conventional commits, but only the PR number is read from them.
- **Direct commits on main are not in the notes.** The preview lists them as uncovered so the summary can mention them; a release with only direct commits is refused.
- **A change archived outside its PR's merge commit** (archived directly on main, or after the PR merged) has no PR number, so its items are listed as written; an item can name its PR itself.
- **The release workflow is unchanged.** `verify-tag` still publishes the tagged `## <tag>` section verbatim (ADR-0026).
- **git-cliff and `cliff.toml` are gone**, as are the `changelog` mise task and the `--unreleased`/`--latest` options.
- **Reversal cost:** medium. Archived sections stay readable; only the reader and `prepare`'s insert would change. The rewritten history stays in `CHANGELOG.md`, and the old text stays in git history (`CHANGELOG.md` at `v0.6.0`).
