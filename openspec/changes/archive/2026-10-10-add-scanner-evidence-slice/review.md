## Findings

### Critical (blocking)

None.

### Moderate

**M1. Switching off during a start waits for `vision.start()`, which has no bound.** Design D2 says that when the switch flips mid-start, teardown happens "once the current step returns". Flow & State Gaps adds that starts are serialised through one lifecycle future chain. `VisionService.start()` (`vision_service.dart:201-207`) has no deadline. It completes only when the worker sends `_Ready` or `_OpenFailed`, and opening the runtime hashes every bundled file and loads the OCR model. If the open hangs (for example a stalled disk, or antivirus holding the 20 MB traineddata), the start step never returns. Three things follow:
- The state stays `starting` after the user switched off.
- A later switch-on queues behind the hung chain.
- `AppServices.dispose`, which disposes the coordinator first, never reaches `database.close()`.

This contradicts the spec's "Worker drain incomplete at shutdown: disposal completes after the drain bound". The service already has a bounded way out: `close()` during `starting` completes `start()` with `VisionWorkerStartFailure('Service closed.')` (`:432-434`) and is bounded by the 2 s drain. So the bound already exists in the service; the design just doesn't call `close()` while the start is still running.

**M2. Switching live scan off depends on the settings write succeeding, so a database failure can keep the global hook installed.** D2 says "a failed save reverts the switch" for both directions. The coordinator reacts to `SettingsController` only after `save` succeeds (`settings_controller.dart:25-42`, where `_settings` changes only after `database.saveSettings`). `save` also returns false, with no error text, whenever another save is `busy`, for example a mode or map change (`:26`). If the user switches off while the database write fails or is busy, the `WH_MOUSE_LL` hook stays installed against the user's explicit choice. This is the T6 risk the design names. The scanner-evidence spec covers a failed save only for switching on.

**M3. The end state is undefined when the targeted capture fails with a fallback-eligible failure and the fallback pass also fails.** D4 starts a fallback after `RoiOutsideClient`, `BlankCapture` or `TargetChanged`, with `targeted: null`. Both the per-scan state diagram and the spec ("Fallback capture fails: … the scan ends `rejected` with the targeted outcome") end a failed fallback as `rejected` with the *targeted outcome*. When the targeted pass was a capture failure there is no targeted `RecognitionOutcome`, and `ScanRejected` has nothing to carry. This is a common case: a blank capture of the targeted region (for example in exclusive fullscreen) is usually followed by a blank full-client capture. The same gap applies when the fallback vision request is not delivered after a targeted capture failure.

**M4. The main `vision-runtime` spec still forbids what this change does.** `openspec/specs/vision-runtime/spec.md:122-127` says normal launch SHALL NOT open any vision library ("WHEN the application starts without the self-check argument THEN … no vision library is loaded"). With live scan saved on, a launch without the self-check argument loads the vision runtime through the pipeline. The change updates the equivalent rules in `vision-worker` and `inspection-recognition` but has no `vision-runtime` delta. After archive, the main specs contradict each other and the shipped behaviour. (`scan-triggers` already allows "unless a trigger consumer starts it", so it needs no change.)

**M5. Timing log schema v1 does not define per-pass stage keys, but the M4 latency gate needs them.** The spec lists stages "per pass" and expects "no fallback stages" for a targeted accept, so the stages must be keyed per pass. D7, however, defines one `ScanTimeline` with "one field per stage". It takes the job sub-stage stamps only "from the evidence of the winning pass". The log example is a flat `"ms":{"captureRequested":…,"published":…}`. When the fallback wins, the targeted pass's capture, vision and matching times are either overwritten or not recorded. Yet the targeted-then-fallback cost is exactly what M4 will measure. ADR-0013 freezes this format (reversal cost: medium), so it should be settled before apply.

**M6. A pending trigger started after a capture timeout fails at once with `captureBusy`.** D3 says that at the capture stage the pending trigger starts "when that capture answers, within the 500 ms deadline". The ledger justifies waiting with "a capture admitted early would answer `captureBusy` and lose the newest click". But when the answer is `CaptureTimeout`, `CaptureService` is in `overrun` and answers every request `CaptureBusy` until the worker replies (`capture_service.dart:226-228, 391-395`). So the newest click is lost in exactly the slow case the wait was meant to cover. The first scan after activation includes the worker spawn and platform open inside the same 500 ms deadline (Flow Gaps, last bullet), so this case is likely. `CaptureService` exposes no "idle again" signal, so the design has to choose one of these:
- add a minimal signal;
- or accept the loss and record it as such.

**M7. The narrowed capture audit will reject the evidence panel, which contradicts the "allow-list is exactly one file" claim.** `capture_source_audit_test.dart:255-258` bans any import of `data/capture/` from `lib/application`, `lib/ui` and `lib/main.dart`. D9's `ScanReport` holds "capture/vision failure" values. The scanner-evidence spec requires the panel (in `lib/ui/`) to show reasons such as `targetNotForeground`. Pattern-matching on `CaptureFailure` subtypes, which the repo's `dart-use-pattern-matching` rule favours, requires that import. The vision audit regex `VisionService` (`vision_worker_audit_test.dart:15`) also matches `VisionServiceState`. Unless the design says how failures reach the UI, the implementer will either widen the audits beyond one file or break them. Those audits are a safety guard (Risks, last bullet).

### Suggestions

- **S1. Name how worker loss is detected.** The spec scenario "Vision worker exits while live scan is `ready`" has no scan in flight, so detection on the next scan (Failure table) is not enough. `VisionService.workerExit` and `CaptureService.workerExit` are the signals that exist. The coordinator must ignore exits caused by its own `close()`, keyed by the activation token.
- **S2. Record that `hookStop` blocks the UI isolate for up to 1 s.** `bgc_hook_stop` joins the hook thread with `WaitForSingleObject(g_thread, 1000)` (`windows/capture/hook.cpp:330`) and is called synchronously from the UI isolate. So the `stopTimedOut` path freezes the UI for 1 s on switch-off, on dispose and again on the retry at switch-on. The proposal's exit criterion says no slow native call can freeze the UI. Also, after a `stopTimedOut`, switching on again loads the template and the full vision runtime before `start()` discovers `AlreadyStarted`. Checking the stuck hook first would avoid that.
- **S3. Build the title index only while live scan is on.** As written in D6, every catalog snapshot change, including the one at startup, runs a full `Isolate.run` index build even when live scan is off.
- **S4. Correct the crop bound.** Resource Bounds says "one decoded image" and "≤256 KiB gray per report". But `recent` keeps up to 10 full `ScanReport`s, each with both passes' evidence: up to 1 + 8 entries at up to 256 KiB each (`inspection_evidence.dart:13`). That is about 23 MiB at the bound. Either keep crops only on `latest`, or state the real bound.
- **S5. Note that the job stage stamps come from evidence entries.** `qpcMarker`/`qpcTitle`/… exist only on evidence entries (`inspection_evidence.dart:116-126`). A `noMarker` or `InspectionRejected` pass did run the marker search but will record it as absent, which the spec's "a stage not reached SHALL be absent" wording does not describe.
- **S6. Fix the error case for a busy save.** `SettingsController.save` returns false without setting `error` when busy. The spec scenario "Setting cannot be saved … an error message is shown" then has no message to show.
- **S7. State where the runtime directory comes from.** The self-check uses `File(Platform.resolvedExecutable).parent.path` (`vision_self_check.dart:176`). The coordinator should use the same, so that "loaded only from the bundle" holds. Also add a Failure-table row for the UI-side capture platform failing to open (missing DLL or hash mismatch) at activation step 3.

## Required Changes

1. **(M1)** In design D2 and Flow & State Gaps, state that switching off (or dispose) during `starting` calls `close()` on any service already constructed at once, without waiting for the current step to return. The pending `vision.start()` then resolves through the service's bounded close (2 s). The hook step is skipped when the token is stale. In the scan-pipeline spec scenario "Switching off during start", replace "once the start finishes" with a bound: "within the vision service's close drain, the worker is closed, no hook is installed, and the state is `off`".
2. **(M2)** In design D2, the scan-pipeline spec and the scanner-evidence spec: switching off SHALL stop the pipeline at once, whether or not the setting is saved. A failed or busy save when switching off shows an error that the preference was not saved, leaves the switch off for the session, and does not reinstall the hook. Add a scenario "Setting cannot be saved when switching off". Keep the existing revert behaviour only for switching on.
3. **(M3)** In design D4 and the per-scan diagram, and in the scan-pipeline requirement "Fallback pass runs when the targeted pass is not accepted": when the targeted pass ended in a capture failure and the fallback pass also fails (capture failure or vision not delivered), the scan ends `failed` with the fallback failure and records the targeted capture failure. Add a scenario for it, for example targeted `blankCapture` followed by fallback `blankCapture`.
4. **(M4)** Add `specs/vision-runtime/spec.md` with a MODIFIED "Normal app launch does not load the vision runtime". The runtime is loaded only by the self-check, by tests and by the scan pipeline while live scanning is on. Normal launch with live scanning off loads no vision library. Keep the "Unknown argument" scenario, qualified by live scanning off.
5. **(M5)** In design D7 and the timing-log data flow, define the v1 `ms` object with per-pass keys: for example `targeted.{captureRequested, acquireStart, acquireEnd, captureAnswered, visionSubmitted, jobStarted, marker, title, preprocess, ocr, jobFinished, matchStarted, matchFinished}`, a matching `fallback.{…}`, plus top-level `trigger` and `published`. State that each pass's sub-stage stamps come from that pass's own evidence (the winning or first entry of that pass). Align the scan-pipeline timing requirement and its scenarios with this shape.
6. **(M6)** In design D3 and the Mechanism Ledger, define what happens when the in-flight capture answers `captureTimeout` while a trigger is pending. Either add a `CaptureService` signal that completes when the overrun worker replies, and start the pending trigger then (bounded by the 2 s drain), or state that the pending trigger ends `failed` with `captureBusy` and is logged. Fix the ledger's justification to match. Add the matching scan-pipeline scenario.
7. **(M7)** In design D9 and Risks, state that `scan_coordinator.dart` (the only allow-listed file) maps capture and vision failures into UI-facing values defined there (for example an enum or a reason code plus message). As a result, no other `lib/application`/`lib/ui` file imports `data/capture/` or names `VisionService*`. Note the audit's regex reach for `VisionServiceState`.
